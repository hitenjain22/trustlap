# Decisions

## Core stack (SPEC 3.2)

| Decision | Choice | Why | Rejected alternative |
|---|---|---|---|
| Sim + training language | Python + **JAX** (with Flax Linen, Optax, Distrax, Chex) | `vmap` + `jit` + `lax.scan` let the whole env and PPO run on GPU with tens of thousands of cars; PureJaxRL proves the pattern | PyTorch (fine, but vectorized envs + training loop fusion are clunkier); Brax/MJX (3D rigid bodies, overkill) |
| Vehicle model | Dynamic bicycle model with simplified Pacejka tires, friction ellipse, drag, rolling resistance, wind, steering lag, action delay | Real tire-slip behaviour (drifting, understeer in rain) at tiny compute cost; textbook model you can explain in an interview | Kinematic model (no slip, so adaptation is pointless); full 4-wheel model (slow, harder to port) |
| Policy size | MLP **3 × 128**, ELU | Enough capacity for this task; small enough for live browser inference for ~64 cars at 20 Hz in plain TypeScript | 256-wide (4× slower in browser); RNN policy (harder to port and train) |
| Adaptation module | MLP over flattened history (H = 20 steps) | Simplest to train and to port; RMA works with this | 1D conv / GRU (more to port, little gain at this scale) |
| Browser inference | Hand-written MLP in TypeScript over `Float32Array`s, in a Web Worker | Zero dependencies, tiny bundle, exact control for parity tests | onnxruntime-web / TF.js (heavy bundles; threading needs COOP/COEP headers) |
| Rendering | **Canvas 2D** with batched paths, `devicePixelRatio` aware | Hundreds of cars + rain particles at 60 fps with zero dependencies | PixiJS/WebGL (big dependency, unnecessary at this scale); SVG (too slow for many moving objects) |
| Charts | Hand-built SVG React components using `d3-scale`, `d3-shape`, `d3-array`, `d3-hierarchy` (math only, React renders) | Full control to meet the chart spec in SPEC 11.6 | Recharts/Chart.js (fighting defaults to hit the spec) |
| Web framework | **Vite + React + TypeScript (strict)** + React Router | Fast, boring, static output | Next.js (static-export edge cases, not needed) |
| Styling | Tailwind CSS with design tokens defined as CSS variables (SPEC 11) | Speed + consistency | Unstyled CSS modules (slower to build consistently) |
| State | Zustand store + URL query params for shareable state | Tiny, simple | Redux (overkill) |
| Worker RPC | Comlink | Clean typed worker calls | Hand-rolled postMessage protocol |
| Schema validation | zod (web), pydantic or dataclasses + manual checks (python) | Fail loudly on bad artifacts | None |
| Tests | pytest (sim), Vitest (web unit + parity), Playwright (e2e + screenshots) | Standard | — |
| Hosting | Vercel static (free), artifacts served from `/artifacts/v1/` with long cache headers | Free, fast, preview deploys | GitHub Pages (base-path quirks) |
| Checkpointing | `flax.serialization` msgpack (or Orbax) to Google Drive / Kaggle output every N updates | Colab disconnects | Keeping everything in RAM |

## Later decisions

### 2026-10-10 (M0)

- **Tailwind v4 instead of v3 (`tailwind.config.ts` → CSS `@theme`).** v4 is the current release; it configures through CSS (`@import "tailwindcss"` + `@theme`) and a first-party Vite plugin, so there is no `tailwind.config.ts`. The design tokens in SPEC 11.2 still live as CSS variables in `web/src/styles/tokens.css`, which is the spirit of the spec. Rejected: pinning v3 just to match the filename.
- **`ruff format` instead of black.** Ruff's formatter is black-compatible and we already depend on ruff for linting: one tool, no extra dependency.
- **Local JAX is 0.4.38 on Intel Mac.** Google stopped publishing macOS x86_64 jaxlib wheels after 0.4.38. Local dev (CPU tests, golden-file generation on CPU) runs on that version; CI (Linux) and Colab/Kaggle install the latest. Consequence: write code against APIs present in both (avoid features newer than jax 0.4.38 / flax 0.10). Pin exact versions after the first working Colab install (SPEC M0.3) and record them in `RUNBOOK.md`. If a needed API is missing locally, develop in a Linux container or Colab instead of bumping the floor.
- **Node 24 LTS**, installed user-locally at `~/.local/share/node` (no Homebrew on this machine). CI uses `node-version: lts/*`.
- **Dev dependencies beyond the spec list:** `@tailwindcss/vite` (Tailwind v4's build integration), `typescript-eslint` + `eslint-plugin-react-hooks` + `eslint-plugin-react-refresh` (the Vite template's lint set), `eslint-config-prettier` (stops eslint and prettier fighting), `jsdom` (DOM for Vitest component tests).

### 2026-10-11 (M1)

Spec changes (each one fixes something in the spec that was wrong or ambiguous; flagged to Hiten at the M1 checkpoint):

- **Curriculum interpolation (SPEC 6.2).** "nominal ± d · half-width, clipped to the full range" never reaches the full range when the nominal isn't the range's center: tire wear would top out at 0.125 (not 0.25), wind at 5 m/s (not 10), μ_dry would never go below 1.005. Now each bound moves linearly: `lo(d) = nominal + d·(lo − nominal)`, `hi(d) = nominal + d·(hi − nominal)`. Identical at d = 0 (the nominal point) and d = 1 (the full range). `config.Range.at_difficulty`.
- **Generated tracks get the drawn-track auto-fix (SPEC 6.1).** With the spec's parameters only 18% of first attempts pass the 18 m minimum-radius check (median tightest corner 11.6 m), so seeds needed many retries and some would eventually hit the 50-attempt limit. Generation now applies the spec's own "Auto-fix" (Laplacian-smooth the control points, λ = 0.3, up to 10 passes) before giving up on an attempt. Measured on 300 seeds: 93% valid on the first sub-seed; 90% of tracks still have a corner tighter than 30 m (median tightest 23 m); median length 1,074 m (was 1,235 m). The full banks needed at most 3 attempts. Rejected: loosening the radius limit (changes the car/track contract) or raising max_attempts (keeps the 82% waste and still risks a raise).
- **Closed-loop resampling (SPEC 6.1.6).** An exact 2.0 m spacing can't tile a loop of arbitrary length. `N = round(L / 2)`, spacing `ds = L / N` (within 0.1% of 2 m). The bank stores `length[T]` so `ds` is exact per track.
- **Curvature definition (6.1.7).** Raw κ_i is the signed angle from tangent i to tangent i+1 over ds, then a 5-point circular moving average (order of summation fixed for the TS port).

Pinned interpretations (the spec allowed more than one reading):

- **Action buffer `[4, 2]`** holds the 4 *previous* actions, newest first. D = 0 executes the current action; D = k executes `buffer[k − 1]`. Covers the OOD delay of 4.
- **Drive and brake hardware are fixed** at the nominal-mass values (`F_drive_max = 7,000 N`, `F_brake_max = 1.3 · 800 · g`), so a heavier car accelerates and brakes worse. Mass and yaw inertia scale with the mass multiplier.
- **Low-speed blending runs right after the velocity update and before the position update**, within each substep, so positions integrate the blended velocities.
- **Gust noise is an input** to `dynamics.control_step` (a standard-normal pair), keeping the step deterministic for golden files. The env draws it from `jax.random`.
- **Puddle arclengths are measured from the episode's start**, so a car never spawns inside one.
- **Spin and stall timers are integer step counters** (crash after the 21st consecutive step beyond 100°, stall after the 61st below 1 m/s) to avoid float drift in the "> 1 s" / "> 3 s" checks.
- **Wrong way** terminates with no penalty beyond the negative progress reward (the spec's termination table gives it none).
- **PCG32** uses the reference seeding with stream 54 (so seed 42 reproduces the reference demo's first outputs); `next_int` uses the modulo method; `splitmix32` is the 32-bit SplitMix variant (constants in `rng.py`).

Implementation choices:

- **One single-car implementation, two array backends.** `dynamics.py`, the core of `env.py` and `scripted.py` take an `xp` argument (`numpy` or `jax.numpy`). JAX runs them `vmap`ped on GPU/CPU; the benchmark's "naive NumPy loop" calls the same source per car. No second implementation to keep in sync.
- **Scripted driver (SPEC M1.6).** Pure pursuit alone (0.5 s lookahead) oscillated into spins; the car model is neutral-steer (identical normalized tire curves front and rear) and rear-wheel drive, so throttle in a corner causes power oversteer. The driver now uses: a 1 s lookahead (8–40 m) with yaw-rate damping; a corner-speed plan at 85% of true grip with braking planned at 45% of μ·g; a speed controller that requests an acceleration (3 m/s² per m/s of error) converted through the car's force limits; and throttle/brakes capped to 80% of the grip that cornering leaves free (friction circle). Tuned on the validation bank only. Result: 100% dry / 99.1% wet completion on all 2,000 training tracks.
- **Observation (not changed):** the specified car is close to neutral steer and quick to power-oversteer. That's realistic for a light rear-drive race car and makes throttle control part of the learning problem. If PPO struggles with it in M3, the conventional fix is a slightly stiffer rear tire (B_rear > B_front) for mild understeer; not done now because nothing requires it.
- **Headline speedup definition.** "GPU vs CPU" compares the *same compiled JAX code* on the T4 and on the same Colab machine's CPU (2 vCPUs) at the same car count; the NumPy loop row is reported separately as the "naive Python" baseline and only at sizes we measured (≤ 1,024 cars). Stated alongside the number wherever it appears, because a laptop CPU is ~4× faster than Colab's (131k vs 28k steps/s).
- **`sim/results/`** (committed) holds small result files from GPU runs, such as `bench_t4.json`; `export.py` copies them into the web artifacts.
- **`rollout.py`** (new module): one-lap-per-car evaluation with no auto-reset, shared by the scripted check now and `evaluate.py` in M6.

### 2026-10-11 (M2)

- **Golden fixtures live in `web/tests/parity/golden/`, not `web/public/artifacts/v1/golden/`** (SPEC 9.1). They're test data: no reason to deploy 6.7 MB of fixtures or count them against the artifact budget.
- **Three extra fixtures** beyond SPEC 9.4: `env_step` (progress, reward, termination flags), `scripted` (actions) and `scripted_closed_loop` (10 runs × 400 steps). The browser runs the env and the scripted driver from M2 on, so they get the same guarantee as the physics. Env fixtures carry a random history only for the first 32 cases (the rest are zeros) to keep the files small.
- **Stale-fixture guard.** `config.physics_hash()` covers every section the browser reproduces; fixtures record it and `sim/tests/test_export.py` fails if the physics changed without `python -m trustlap.export --golden`. This enforces SPEC rule 2 in CI.
- **Interim hero copy.** In M2 the cars run the hand-written scripted driver, so the spec's headline ("These cars taught themselves…") would be false. The hero says what is true now ("Watch 48 cars race through the rain, live in your browser"; body names the scripted driver). Swap in the final copy when trained drivers run in the hero (M3/M5). Story steps 2–5 are marked "In progress" and written in the future tense.
- **Display type size in the hero is `clamp(34px, 3.4vw, 52px)`** instead of SPEC 11.4's `clamp(44, 6vw, 76)`: at 76 px the headline didn't fit the 560 px text panel on a 720 px-tall laptop screen. Weight, width axis, leading and tracking are as specified.
- **Cars are drawn at least 13 CSS px long.** At whole-track zoom a 4.4 m car is 3–5 px and reads as a dashed line. Purely visual, like the dots on a broadcast track map; physics is unchanged.
- **No backdrop blur behind the hero text.** A `backdrop-filter` over an animating canvas has to be recomputed every frame; removing it took the retina hero from 36 to 60 fps in the measurement. The panel uses a solid `--asphalt` at 80% instead (SPEC 14.5 asks for 70%; the extra 10% keeps contrast now that nothing blurs the rain behind it).
- **The hero picks its showcase track by shape**: the export records each track's bounding-box aspect ratio, and the page chooses the one that best fits the free screen area (landscape laptop vs portrait phone).
- **Browser puddles belong to the track.** Their layout is seeded per track and shared by every car (they're drawn once); the rain level decides how many are wet (`round(R · 8 · 0.75)`, the training mean). Training still samples puddles per episode.
- **Browser driving is continuous.** Laps roll over, a crashed car fades for 0.6 s and respawns 30 m back on the centerline, and there is no time limit. Each scripted car gets a slightly different style (grip use ×0.86–1.0, braking ×0.85–1.05, lookahead ×0.9–1.15) so the field spreads out instead of driving in lockstep.
- **Snapshot buffers ping-pong** between worker and main thread (transferred both ways) so the worker doesn't allocate a new array every tick.
- **One cached background per frame**: static layers + wet sheen + skid marks are composed into one offscreen canvas, rebuilt when the track, size or rain changes (and every 60 s, which also clears old skid marks). Kerbs are batched into one path per color. Together with the blur fix this took Lighthouse performance from 91 to 100.
- **Kerbs sit on the inside of corners** (apex kerbs), where SPEC 11.7 leaves the side open.
- **The nav only lists pages that exist.** Training lab, Results and How it works join it when they're built.
- **Tests get their own `tsconfig.test.json`** (adds Node types for reading fixtures); app code still compiles without Node types.
- **No frontend design skill was available** in this environment (SPEC 0 asks to load one if present); the UI follows SPEC 11 directly.
- **Benchmark CPU sizes** keep 65,536 cars (with fewer fused steps for big CPU batches) so the GPU/CPU headline always compares like for like at the largest size.

### 2026-10-11 (overnight: M3–M6, made autonomously while Hiten slept; review in the morning)

Compute (the big one):
- **All training ran on the laptop CPU at reduced scale**, because GPU training needs Hiten's Colab/Kaggle account. Measured PPO throughput ≈ 17k env steps/s (1,024 envs, 4 CPU threads). Budgets: blind 40M steps (single agent; SPEC 7.8's P = 8 small PBT skipped), teacher PBT P = 4 × 20M steps (SPEC: 16 × 100M), students K = 5 × 8M steps (SPEC: 5 × 40M). SPEC 7.9 lists these knobs; every number on the site states the compute it came from. Full-size GPU runs can replace these artifacts later without code changes.
- **Training chain is a detached shell script** (`sim/scripts/overnight_pipeline.sh`) so it keeps going even if the Claude session is interrupted; each stage resumes from its checkpoint.

Learning:
- **Value loss is plain MSE** (no value clipping); SPEC 14.3 lists clipping as a last resort, and explained variance stays ≈ 0.9.
- **Curriculum success counts only cars at the curriculum difficulty** (the 20% easy cars at d = 0 are excluded once d > 0), otherwise easy laps inflate success.
- **Stretch resets** pick one condition uniformly and set it to the *harder* edge of its current range (the one farther from nominal).
- **PBT fitness** = mean progress per second over finished episodes in the 25-update window (as specified). The "watch it learn" snapshots save the *best current member* at 12 evenly spaced points, not the final winner's ancestor chain (simpler; the difference is cosmetic for a timeline).
- **NaN guard**: a non-finite car is reset and counted; the run aborts if NaN resets exceed 0.1% of episodes after update 5.
- **Students**: DAgger rollouts use the teacher's *mean* action fed ẑ (or z with probability β in the first 10%); no exploration noise. Grip labels are the true axle μ recovered from the privileged vector. Students train at the teacher's final curriculum difficulty with the same easy/stretch split.

Evaluation:
- **Puddle step-response latency** is defined as: time from the true rear grip first dropping by more than the 0.1 tolerance, until |μ̂_rear − μ_rear| < 0.1 (SPEC's "from entering the puddle" is ill-defined because at the edge the error is still small). Trials vary entry speed 18–22 m/s and lateral offset ±1.5 m. The straight is a 700 m stadium loop.
- **Governor τ** is chosen on the validation bank: the lowest crash rate whose paired lap time is at most 5% slower than ungoverned (falls back to the middle τ if none qualifies). The sweep chart is reported on the test bank.
- **Calibration** is fit on validation rollouts of five suites (combined, puddles, wet, ice, extreme_lag), so it covers in- and out-of-distribution risk; ECE/Brier/AUROC are reported on test rollouts of the same suites.
- **"Crash" for calibration and the crash-rate metric** includes off-track and spins; stalls and wrong-way count as crashes in the evaluation outcome too (they are failures of the lap).
- **Rollouts stop early** when every car has finished (chunks of 200 steps): identical results, much less CPU.

Browser:
- **Hero runs the student with one ensemble member** (48 cars × 5 students would be too heavy for phones); the Playground runs all five and shows the crash-risk estimate. Falls back to the best shipped driver when a network is missing.
- **Each hero car gets a slightly different car** (power ×0.94–1.0, mass ×1.0–1.06, inside the training ranges) so identical deterministic drivers spread out instead of driving nose to tail.
- **Which drivers a build offers comes from `manifest.json`** (data-driven, no hand-kept list).

### 2026-10-11 (daytime: M6–M7)

- **Evaluation uses 2 condition draws per track** (200 tracks × 2 = 400 laps per driver per suite) instead of 3, a SPEC 7.9 reduction; stated on the Results page.
- **Bug found and fixed in evaluation**: the compiled-rollout cache captured the first track bank it saw, so training-bank runs reused test-bank geometry (generalization showed 2.5% vs 30%). The bank is now a jit argument; regression test in `tests/test_evaluate.py`. The full evaluation was rerun so every number comes from one coherent run.

- **Negative and undefined headlines are shown as such**: the crash-reduction tile flips to "More crashes than the blind driver" when negative; the teacher-gap tile says "not meaningful" when the teacher didn't beat the blind driver (the formula's sign flips there).
- **Chart titles state findings only when data exists**; missing data gets a neutral title plus "Not computed yet".
- **The Lab's learning-rate chart shows the base rate** (the logged value includes the scheduled linear decay; PBT tunes the base).
- **README numbers are generated** by `export.py` from `metrics.json` between `<!-- metrics:start/end -->` markers (SPEC rule 4).
- **OG image** is a real frame of the live simulation (canvas pixels, not an element screenshot, which would include the page text) plus the wordmark and headline, made by `web/scripts/og-image.mjs`.
- **Full-size GPU pipeline** (`sim/scripts/full_pipeline.sh`, `sim/notebooks/train_full.ipynb`) runs the SPEC 7.9 budgets with resume-on-restart; it's the recommended way to replace tonight's CPU results.
- **Puddle step-response metric corrected.** The first definition (time until |μ̂_rear − μ_rear| < 0.1 after the grip drop) was also satisfied when the car simply *left* the puddle, so it reported a misleading "350 ms". Now "noticed" means the estimate has fallen by at least half of the true drop; trials where that never happens count as not noticed and the count is reported. Result: 0 of 200 on a straight, and 0 of 100 in an extra mid-corner test (`puddle_s_m=857` on the stadium bend). The site, README and explainer now say the student doesn't detect individual puddles, and that its better wet/puddle completion isn't explained yet (plausibly caution inherited from the teacher, untested).
- **Drawn tracks (SPEC 6.1).** The pointer stroke is first scaled to a nominal 1,750 m so RDP's ε = 1.5 m means meters (ε grows ×1.5 until ≤ 30 points; resampled up to 8 if fewer), then centered and scaled so the spline length sits in [1.15 × min, 0.9 × max]. Width is the middle of the width range; puddle placement uses a fixed seed (0) since a drawn track has none. **Auto-fix deviates slightly from the spec:** Laplacian smoothing (λ = 0.3, ≤ 10 passes) shrinks the loop, so each pass re-fits the length; without that, smoothing a tight drawing turned "too tight" into "too short". The tail of the stroke inside the closing circle is trimmed so overshooting the start doesn't leave a hook.
- **Bug found while testing drawn tracks:** RDP measured perpendicular distance to the start–end chord, which is zero-length for a closed stroke that ends exactly on its start (as real pointers do), so everything collapsed to NaN geometry that then passed validation (NaN comparisons are false). RDP now measures from the point when the chord is degenerate, and non-finite tracks are rejected. Unit tests cover both; the e2e test draws a figure eight (rejected: crosses itself) and an oval (accepted, raced on).
- **Copy link and the shortcuts button moved to the top of the conditions panel** so the Playground toolbar fits one row at 1280 px; the seed label shows from 1536 px up.
- **Load-time long tasks (M7 follow-up 4): mostly browser cold start, one small fix.** Traced at DPR 2 (Chrome trace + CPU profile + per-section frame timers). What blocks the main thread at load: (1) evaluating the main JS module, ~56 ms, which is almost entirely react-dom, react-router and zod initializing (app code is ~2k of ~25k lines in that chunk); (2) the first frames that touch each canvas, whose cost is GPU cold start, not drawing: in headless SwiftShader the same frame measured 215 ms in one run and 25 ms in the next (shader JIT on first use), and on the real Intel GPU (Metal) the very first `fillRect` took 1.2 s in Playwright's fresh profile (context + shader compile, no shader cache). App code can't remove either. The fix that was ours: `z.config({ jitless: true })`, since zod 4 JIT-compiles every object schema on first parse and every schema here parses once (config.json first parse 5.5–12 ms → 3–4.6 ms in Node; it also drops `new Function`). Not done, judged not worth it: splitting zod out of the main chunk (Home needs the config schema), or staggering background/rain warm-up across intro frames (the cost moved around between runs, so the gain couldn't be shown).
